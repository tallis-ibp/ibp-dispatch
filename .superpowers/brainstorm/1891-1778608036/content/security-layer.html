Security Layer

Section 2 of 3 — Every entry point locked down. Does this cover your concerns?

🖥️ Dashboard Access
  • JWT token — scheduler logs in once, gets a signed token
  • Token expires in 24h — must re-login
  • All /api/* routes reject requests with no valid token
  • Login page is the only unauthenticated route
  • No user accounts DB needed — one env var password
📱 Telegram Webhook
  • Secret token validated on every webhook call
  • Requests without the secret → 403, ignored
  • Scheduler commands only accepted from one known chat ID
  • Crew commands only accepted from registered group IDs
  • Unknown senders flagged, never executed
🔒 API Input Validation
  • Zod schemas on every API endpoint
  • Date params must match YYYY-MM-DD — rejects garbage
  • Crew keys validated against known list
  • No raw SQL — SQLite via parameterized queries only
  • Invalid input → 400 with clear error, never crashes server
🚦 Rate Limiting
  • Max 60 requests / min per IP on all routes
  • Max 5 login attempts / min on auth route
  • Exceeded → 429, auto-unlocks after 1 min
  • Prevents brute-force on login + API abuse
📁 File & Photo Security
  • Photo paths resolved with path.resolve + prefix check
  • Path traversal (../../etc/passwd) → 400, blocked
  • Static files served from a whitelist of safe dirs only
  • No user-controlled filenames ever written to disk
🔑 Secrets & Environment
  • All secrets in .env — never hardcoded
  • Server validates all required env vars on startup — crashes fast with a clear message if any are missing
  • Logs never print tokens, API keys, or chat IDs
  • .env in .gitignore — never committed
What this does NOT cover (out of scope for now):   Multi-user roles (admin vs. viewer)  |  End-to-end encryption of stored data  |  SOC2 / compliance auditing  |  DDoS protection beyond Railway's built-in limits
